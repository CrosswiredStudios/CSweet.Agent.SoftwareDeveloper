# 2.3.0

The engineer can now observe interactive behavior the same way QA does, before handing work off.

From Super Awesome Games ticket VGD2A04892DB-38 (2026-11-13), which failed QA twice in a row on the same spike harness.

- **Before.** The only browser tool was `check_browser_build`, which shows the page loaded without exceptions. The
  harness page decided its own scenario results from what the code intended: a planned brick path, and a voice cap
  counted only when a sound was booked. The observation record copied those intended values, and QA found one mismatch
  per round.
- **Now.** A ticket whose planning declares `browser-interaction` must carry a passing run of the shared browser
  scenario runner (CSweet.Agent.SDK 5.25.0).
  - New tool `run_browser_scenarios(buildDirectory, observationRecords)`. It writes the trusted runner to
    `.csweet/browser-scenarios.cjs` and runs it in real Chromium.
  - The runner, not the page, judges each check from its expected and observed values, and fails a check whose
    observation cites no emitted event.
  - It regenerates the measured section of every named observation record.
  - The passing receipt is added to the validations automatically. Without it, publication fails with a clear entry,
    as with the browser-smoke receipt.
- **Prompt.** The assignment explains the browser scenario contract for those tickets:
  - measure observations from emitted events, never from the plan;
  - make every computed invariant a check;
  - keep reasoning from source outside the generated section.
- **Packages.** `CSweet.Agent.SDK` 5.25.0 and `CSweet.WorkManagement.Contracts` 5.6.0.

Validation: `dotnet test` 375 passed, 0 failed, including new `BrowserScenarioCheckTests`.
