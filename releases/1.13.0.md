# 1.13.0

- Give every prior review finding a stable ID in the coding prompt and require the completion report to answer each one as `fixed`, `already-resolved`, `disputed` or `needs-decision`, with evidence.
- When validated rework leaves the workspace unchanged, resubmit the exact previously published candidate for review with per-finding evidence, instead of blocking on "no reviewable changes".
- When a finding cannot be addressed in code (missing environment, tooling or scope decision), return a Blocked outcome that states the decision needed, the unchanged candidate and the options, tagged `decision-required:v1`. Architecture support is not requested for decisions.
- Remember each published candidate per assignment, falling back to this developer's earlier publication evidence comments. Unchanged work in a replacement sprint (for example after an owner scope amendment) then resubmits the retained candidate instead of stalling.
- Resubmit an unchanged candidate at most once per disagreement. If review rejects the same resubmitted build again, escalate for a tie-break instead of looping, and follow the manager's retry direction when one is given.
- Read the manager's retry directions for the exact stage from assignment evidence and include them in the coding prompt.
- Ask the team's technical lead for technical support: the Architect, or the Technical Director on game teams. The lead's full guidance (diagnosis, steps, invariants, verification) is remembered for the exact stage and included in the retried coding prompt; previously only a receipt reached it.
- Reject inconsistent reports that claim fixes without changes. No new capabilities, grants or network access.
